# 一、使用者体验问题

## U-1　识别结果不可干预，OCR 噪声直接进入 AI 提示词　`P0`

**现象**　选完图片立刻跳转 `OcrPage`，`initState` 中直接触发整条链路，用户没有任何机会查看、修改、删除识别出的单词。拍课本会把"Unit 3"、页码、断行的半个单词、中文一并塞进"请用这些单词写一篇短文"，产出的故事随之跑偏。唯一补救手段是返回重拍。

**定位**　`frontend_flutter/lib/pages/ocr/ocr_page.dart:18` → `app_provider.dart:52` `recognizeText()` 内部直接续接 `_generateStory(words)`

**为什么严重**　这是 AI 应用的通用铁律：**不给用户修正输入的机会，产品质量就完全押在 OCR 准确率上**。而手机拍摄场景下 OCR 必然有噪声。

**建议**
1. 在 OCR 与生成之间插入一个**单词确认页**：Chip 列表可勾选/取消，支持手动添加与删除。
2. 拆开 `recognizeText()`：识别完成即 `notifyListeners()` 停下，由用户点"生成"再调用 `_generateStory(selectedWords)`。
3. 顺带在此页放"重新生成"按钮，解决生成结果不满意只能重拍的问题。

> 这一条同时解决了 U-1、T-2（双轮 OCR 召回过度）和用户控制感缺失，是全清单性价比最高的改动。

---

## U-2　单词高亮实际未生效　`P0`

**现象**　短文中的目标单词在屏幕上与普通文字**完全没有视觉区别**，用户得对着上方的 Chip 列表自己找。

**定位**
- `story_page.dart:117`　拆出的目标词 span 样式：`TextStyle(color: Colors.black87)`
- `story_page.dart:48/59`　正文基准样式：`...copyWith(color: Colors.black87)`
- 中文侧同理：`story_page.dart:152`
- `history_detail_page.dart` 中为**逐字复制的同一份代码**

两者颜色完全一致，`_buildEnglishSpans` / `_buildChineseSpans` 里 60 多行的正则切分逻辑最终产生了零视觉效果。函数注释写的是 "Build **underlined** TextSpans"，但代码中并无 `TextDecoration.underline`。

**建议**
```dart
// story_page.dart:117 附近
spans.add(TextSpan(
  text: m.group(0),
  style: const TextStyle(
    fontWeight: FontWeight.bold,
    color: Colors.blue,                      // 或
    decoration: TextDecoration.underline,    // 与注释保持一致
    decorationStyle: TextDecorationStyle.dashed,
  ),
));
```
同时把这两个函数和 `_SectionCard` 抽到 `lib/widgets/highlighted_text.dart`，消除 `story_page` 与 `history_detail_page` 之间约 130 行的重复代码。

## U-3　前端 60 秒超时与后端 120 秒等待不匹配　`P0`

**现象**　单词较多或网络较慢时，前端弹出 `Failed to generate story`，但后端其实仍在正常工作。用户白等一分钟，记录也没保存。

**定位**
- 前端　`api_config.dart:5`　`receiveTimeout = 60000`（60 秒）
- 后端　`ai_service.py:17`　`httpx.AsyncClient(timeout=120.0)`（120 秒）
- 且前端需**串行发起两次**生成请求（`app_provider.dart` 中 `generateStory` → `generateFillBlank`），每次都可能跑满后端的 120 秒

**建议**　短期把 `receiveTimeout` 提到 `180000` 并把后端 DeepSeek 超时降到 60 秒，让前端超时**始终大于**后端；长期按 A-1 合并为单接口 + 流式输出，从根上消除这类不匹配。

---

## U-4　降级静默发生，用户无法分辨真假数据　`P0`

**现象**
- OCR 不可用时返回固定词表 `apple, book, cat, dog, english...`（`ocr_service.py:59-63`）
- DeepSeek 调用抛任何异常时返回固定的 "The quick brown fox" 故事（`ai_service.py:34-38`）

用户拍的是自己的课本，拿到一篇关于 fox 的故事，只会以为"AI 理解错了"，而不会意识到服务其实挂了。

**定位**　`ocr_service.py:14`（`auto` 模式静默回落）、`ai_service.py:34`（`except Exception` 吞掉一切）

**建议**　保留降级（它对开发体验很有价值），但**让降级可见**：
```python
# 响应体增加标记
return {"words": result, "degraded": True, "reason": "ocr_unavailable"}
```
前端检测到 `degraded` 时在页面顶部显示黄色提示条："当前为演示数据，识别服务暂不可用"。
另外 `ai_service.py:34` 的 `except Exception` 过宽，至少应把异常类型与内容记入日志而非仅 `print`。

## U-5　保存无反馈且可重复点击　`P1`

**现象**　`StoryPage` 右上角保存按钮点击后无任何提示，用户不确定是否成功，多点几次就产生多条重复记录。

**定位**　`story_page.dart:16` → `app_provider.dart` 的 `saveCurrentRecord()` 不返回结果、不改变状态

**建议**　让 `saveCurrentRecord()` 返回 `bool` 并维护 `isSaved` 状态；成功后弹 `SnackBar` 并把按钮置灰（或图标切为 `Icons.check`）。

---

## U-6　长时间等待无进度、无法取消　`P1`

**现象**　从选图到看到结果可能 30~60 秒，期间只有一个转圈和一句 `Analyzing image...`，用户无法判断卡住还是在跑，也无法中止。

**定位**　`ocr_page.dart:35`

**建议**　最小改动是把 `AppProvider` 的 `_isLoading` 换成阶段枚举（`recognizing` / `writing` / `blanking`），文案相应变为"正在识别单词…/正在创作短文…/正在生成填空…"。配合 A-1 的流式输出，体验提升最明显。

---

## U-7　图片不压缩，原图直传　`P1`

**现象**　手机拍摄的原图通常 3~8MB，未经压缩直接上传，移动网络下耗时且易触发超时。

**定位**　`home_page.dart:56`　`picker.pickImage(source: source)` 未传任何压缩参数

**建议**
```dart
final image = await picker.pickImage(
  source: source,
  maxWidth: 1920,       // OCR 精度足够
  imageQuality: 85,
);
```
通常能把体积压到十分之一，且对 OCR 准确率几乎无影响。

## U-8　后端已实现但前端未接出的功能　`P1`

| 能力 | 后端状态 | 前端状态 |
|------|----------|----------|
| 难度分级 beginner/intermediate/advanced | `ai_service.py` prompt 完整实现 | `api_service.dart:40` 固定传 `intermediate`，UI 无入口 |
| 收藏 `is_favorite` | `PUT /history/records/{id}` 已实现 | 全项目零引用 |
| 笔记 `notes` | 同上 | 全项目零引用 |
| 分页 / 关键字搜索 | `GET /history/records` 支持 `page`/`page_size`/`search` | `app_provider.dart:123` 固定第 1 页 20 条，无翻页与搜索框 |

**影响**　难度选择是这个产品差异化最便宜的抓手（同一批单词给小学生和高中生生成不同难度），后端都写好了却没有入口；历史记录超过 20 条后用户再也看不到。

**建议**　优先补**难度选择器**（放在 U-1 的单词确认页上，三个 Chip 即可）和**历史分页/搜索**；收藏与笔记可延后。

## U-9　详情页无法回看原图　`P2`

**现象**　历史记录里看不到当初拍的那张照片，只能靠短文内容回忆。

**定位**　`app_provider.dart` 中 `imageUrl: _pickedImage?.name` —— 只存了本地文件名，图片本身从未上传或持久化；`learning_records.image_url` 字段名存在误导。

**建议**　后端增加图片存储（本地目录或对象存储），`/ocr/recognize` 返回可访问的 URL；前端 `cached_network_image` 依赖已经装好了，正好用上。

## U-10　界面全英文　`P2`

**现象**　目标用户是中国英语学习者（很可能是中小学生），界面却是 `Recognized Words` / `English Fill-in-the-Blank` / `No records yet`。

**建议**　至少把导航、按钮、状态提示中文化；正文内容保持英文。用 `flutter_localizations` + `intl` 或先简单抽一个 `strings.dart` 常量表。

## U-11　Web 版首屏加载缓慢　`P2`

**现象**　浏览器访问需先下载约 10MB 资源（`canvaskit.wasm` 7.2MB + `main.dart.js` 2.3MB），`static/` 目录总计 46MB。

**注意**　本机 Flutter 为 **3.41.7**，轻量的 HTML 渲染器自 3.29 起已被移除，现在只剩 `canvaskit`（默认）与 `skwasm`（`--wasm`）两条路，**换渲染器已无法解决体积问题**。skwasm 体积相近甚至更大。

另有一个容易踩的点：Flutter 默认从 `https://www.gstatic.com/flutter-canvaskit/<revision>` 远程加载 CanvasKit（见 `build/web/flutter_bootstrap.js`），该域名在中国大陆不可达。本项目 `static/canvaskit/` 保留了本地副本，**这是必须的，不要为了减小仓库体积而删掉**。

**建议**　在 Flutter Web 框架内能做的只有边际优化：
- Nginx / FastAPI 开启 gzip 或 brotli（`main.dart.js` 2.3MB 压缩后约 600KB，`canvaskit.wasm` 也能压掉一半以上）
- 删掉构建产物里的 `*.symbols` 文件（`canvaskit.js.symbols` 1.3MB + `skwasm.js.symbols` 1.5MB，仅调试用）
- 保留 service worker 缓存，让首次之后的访问不再重复下载

若"发链接即用"是重要场景，真正的解法不是调 Flutter 的构建参数，而是**单独做一个轻量 Web 页面**（详见对 Flutter/Vue 选型的讨论）。

# 二、架构设计问题

## A-1　三次调用的编排逻辑放在了客户端　`P1`（架构层最值得改的一条）

**现状**　`AppProvider` 依次发起 `/ocr/recognize` → `/story/generate` → `/story/fill-blank`，每次都是一个完整的移动网络往返。

**连锁后果**
1. 三次往返延迟叠加，移动网络下白白多花数秒
2. 短文全文从服务端下发到手机、再**原样上传回服务端**去挖空（`generateFillBlank(englishStory, chineseTranslation, ...)`）——同一篇文章在网络上走了三趟
3. 服务端无法做重试、缓存、限流，因为它不知道这三个请求属于同一次学习
4. **无法实现流式输出**——而这是本项目感知延迟最有效的优化
5. 业务规则散落在 Dart 里，将来出小程序或其他端要重写一遍

**建议**　后端新增单一编排接口，前端从"编排者"退回"展示者"：
```python
@router.post("/learn")
async def learn(file: UploadFile = File(...), difficulty: str = "intermediate"):
    words = await ocr_service.recognize(await file.read())
    story = await ai_service.generate_story(words, difficulty)
    blanks = await ai_service.generate_fill_blank(story["english"], story["chinese"], words)
    return {"words": words, **story, **blanks}
```
进一步可改为 SSE 流式推送，把"一分钟白屏"变成"文字逐句出现"。

> 注意：若采纳 U-1 的单词确认页，接口应拆为 `/ocr/recognize` 与 `/learn/compose`（传入用户确认后的词表）两步，而非一步到底。

## A-2　缺少用户模型，数据全局共享　`P1`

**现状**　`learning_records` 单表无 `user_id`，所有使用者共用同一份历史记录。配合 S-1（无鉴权），公网上任何人都能读取、修改、删除他人记录。

**建议**　这不是"加个登录页"能补的，数据模型本身要动。最小可行方案：客户端生成设备 UUID 存入 `shared_preferences`（依赖已装），随请求头下发，后端按 `user_id` 隔离查询。正式方案再上账号体系。

---

## A-3　降级策略的设计哲学需要重新定位　`P1`

**现状**　见 U-4。当前的静默 mock 是"为开发者方便"设计的，但它同时作用于生产环境，于是变成"对用户撒谎"。

**建议**　用配置区分场景：开发环境 `OCR_MODE=auto` 保持静默降级；生产环境 `OCR_MODE=docker`，失败即返回 503 并由前端给出明确错误。`config.py` 已有 `ocr_mode` 字段，AI 侧也应加一个对称的 `ai_fallback_enabled` 开关。

---

## A-4　SQLite 同步调用阻塞事件循环　`P2`

**现状**　`app/models/history.py` 中方法声明为 `async def`，内部却是阻塞的标准库 `sqlite3` 调用。单用户无感，并发上来会拖住整个 Uvicorn worker。

**建议**　二选一，不要两头不靠：
- 启用已在 `requirements.txt` 中的 `aiosqlite`，改为真异步
- 或把方法改回普通 `def`，让 FastAPI 自动丢进线程池

---

## A-5　单一 God Provider　`P3`

**现状**　`AppProvider` 同时承担图片选择、OCR、故事生成、填空、历史列表、删除六件事（151 行）。当前规模完全可控，但每加一个功能它都会变长，且任一操作的 `notifyListeners()` 都会触发全部监听者重建。

**建议**　功能继续增加时按领域拆分为 `LearningProvider` 与 `HistoryProvider`。现在不必动。

# 三、技术选型商榷

> 以下几项**当前方案能用**，列出是因为存在明显更优解，值得在下一次迭代时重新评估。

## T-1　Android 端 OCR 走服务器往返，可以省掉　`P2`

**现状**　手机把数 MB 原图传到服务器 → 服务器转发给 OCR 容器 → 容器跑两轮识别 → 原路返回。用户为此等数秒，项目为此养一个容器。

**替代方案**　Android 可用 `google_mlkit_text_recognition`：端侧识别、离线可用、数百毫秒出结果、零服务器成本。鉴于实际投入使用的形态正是 Android（见提交 `f686c0d`），收益明显。

**权衡**　当前方案换来的是"Web 端复用同一套逻辑"。建议两者并存：移动端走 ML Kit，Web 端回退服务端 OCR。

## T-2　双轮 OCR 使延迟翻倍且只增不减　`P2`

**现状**　`docker/paddle_ocr/server.py:78-89`，原图跑一遍 + 预处理后再跑一遍，结果按小写去重合并。

**评价**　对光照不均的照片确实提升召回，是踩过坑后的务实设计。但代价是识别耗时 ×2，且 `merge_ocr_results` 的策略是**无条件追加新词**——噪声词也一并增多。

**结论**　激进召回必须与 U-1 的单词勾选界面配套（宁多勿漏，用户划掉即可）。目前只做了一半，所以噪声全部流向了 AI。要么补上勾选页，要么给第二轮结果加置信度过滤。

## T-3　Flutter Web 的 CanvasKit 渲染器　`P2`

见 U-11。要点是：**这不是一个配置能修好的问题**，HTML 渲染器已被移除，Flutter Web 在可预见的未来都是十兆级首屏。要不要为此付出代价，取决于 Web 端在产品里的权重。

## T-4　冗余依赖　`P3`

`requirements.txt` 中 `sqlalchemy==2.0.35`、`aiosqlite==0.20.0`、`aiofiles==24.1.0` 在业务代码中**零引用**（已全量检索确认）。要么按 A-4 真正用起来，要么删除。

# 四、安全问题

> 详细分析见[项目架构分析报告](./项目架构分析报告.md)第七章。以下为摘要，**在让第二个人使用本应用之前必须全部处理**。

| 编号 | 问题 | 定位 | 建议 |
|------|------|------|------|
| **S-1** | 静态文件路由存在路径穿越风险 | `backend_fastapi/main.py:35-37` | `os.path.join(static_dir, full_path)` 未校验，编码后的 `..` 可能读到 `static/` 之外的文件（含 `.env`）。改用 `StaticFiles` 挂载，或 `os.path.realpath` 后校验前缀 |
| **S-2** | 全部接口无鉴权 | `app/api/*` | 公网 IP 上任何人可增删改查他人记录。配合 A-2 一并处理 |
| **S-3** | CORS 全开 + 明文 HTTP | `main.py:17`、`AndroidManifest.xml` | `allow_origins=["*"]` 使 `frontend_url` 配置形同虚设；`usesCleartextTraffic="true"` 意味着图片与内容全程明文。收敛来源白名单并接 HTTPS |
| **S-4** | AI 输出未做安全处理 | `ai_service.py` | 模型输出直接渲染。当前用 `RichText` 无 XSS 风险，但若将来改用 WebView 或 Markdown 渲染需先净化 |

# 五、工程化问题

## E-1　构建产物进入版本库　`P2`

`backend_fastapi/static/` 下 36 个文件已被 Git 跟踪，`main.dart.js` 每次重新构建都是 2.3MB 的 diff，仓库会持续膨胀且历史永远清不掉。另有未跟踪的 `static/assets/assets/` 嵌套目录残留，说明手工复制产物的流程本身已经出过错。

**建议**　`.gitignore` 加入 `backend_fastapi/static/`，改为部署时构建；复制步骤写成脚本避免再次出错。

## E-2　后端 Dockerfile 缺失，容器化只完成一半　`P2`

`docker/docker-compose.yml:22` 中 `backend` 服务指向 `../backend_fastapi/Dockerfile`，**该文件不存在**，`docker compose up` 会直接构建失败。README 的 Docker 启动步骤目前只对 OCR 服务成立。

**建议**　补一个标准 Python 镜像的 Dockerfile，顺便把 `data/` 挂成命名卷以免容器重建丢库。

## E-3　测试基本为零　`P2`

- `backend_fastapi/tests/` 为**空目录**
- `frontend_flutter/test/widget_test.dart` 是 Flutter 模板自带的计数器测试，断言 `find.text('0')`，与当前 UI 完全无关，**一跑就失败**

**建议**　优先补三个 Service 的集成测试（`AIService` 的 JSON 解析、`OCRService` 的降级分支、`HistoryModel` 的增删改查），这是后续任何重构的安全网。前端至少把失效的模板测试删掉或改写。

## E-4　AI 返回解析不健壮　`P2`

`ai_service.py` 中 `json.loads(content)` 直接解析，模型若输出 ` ```json ` 代码块包裹就抛 `JSONDecodeError`——**且这一步在降级逻辑之外，会直接 500**。

**建议**　剥离代码围栏，或用正则提取首个 `{...}` 片段，解析失败时也走降级：
```python
content = content.strip().removeprefix("```json").removeprefix("```").removesuffix("```").strip()
```

## E-5　其他　`P3`

- `docker/paddle_ocr/` 内实际运行的是 **RapidOCR**，目录名误导后续维护者，建议更名
- 主文档 `开发者操作文档.md`（约 570 行，内容详实）位于根目录，建议移入 `docs/`
- 数据库无备份机制，`data/english_learning.db` 单文件丢失即全部记录丢失
