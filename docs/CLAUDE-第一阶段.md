## 1. 项目速览

拍照 → OCR 提取单词 → AI 生成含这些单词的英文短文与中译 → 自动生成中英文填空 → 存档 / 收藏 / 导出 PDF。

| 层 | 技术 | 位置 |
|----|------|------|
| 前端 | Flutter（Dart ^3.11.5）、Material 3、`provider`（单一 `AppProvider`）、`dio` | `frontend_flutter/lib/` |
| 后端 | FastAPI + Uvicorn，API → Service → Model 三层，SQLite（标准库 `sqlite3`） | `backend_fastapi/` |
| OCR | RapidOCR 独立容器（目录名仍叫 `paddle_ocr`） | `docker/paddle_ocr/` |
| AI | DeepSeek `deepseek-chat`，失败时降级为 mock | `backend_fastapi/app/services/ai_service.py` |

前端数据流：Page → Provider → Service → Model。三次请求（`/ocr/recognize` → `/story/generate` → `/story/fill-blank`）由 `AppProvider` 在客户端串行编排。

仓库根目录：`D:\all_project\English_Vocab02\english_learning_app`

## 6. 第一阶段任务

建议顺序：**U-3 → U-7 → U-2 → U-5 → U-1**。

理由：U-3、U-7 独立且改动最小；U-2 与 U-5 都会改 `story_page.dart`，先 U-2 后 U-5 减少冲突；U-1 最大且需要确认设计，放在最后，此时 `StoryPage` 已稳定。

### U-3　统一前后端超时

- 现象：前端 `receiveTimeout = 60000`（`api_config.dart:5`），后端 DeepSeek 调用 `timeout=120.0`（`ai_service.py:17`），前端先超时报错，后端仍在工作。
- 要求：前端超时**必须大于**后端超时；把前端 `receiveTimeout` 提到 `180000`。
- ⚠ 后端是否同时降到 60 秒，**见第 9 节待确认项 1**。在我回复前，**只改前端，不动后端**。
- 验收：前端超时数值大于后端；说明每次请求单独计时（两次串行请求各自有自己的超时）。

### U-7　图片压缩上传

- 现象：`home_page.dart:56` 的 `picker.pickImage(source: source)` 未传压缩参数。
- 要求：传入 `maxWidth: 1920`、`imageQuality: 85`。先确认相机与相册是否共用同一处调用，避免漏改。
- 报告称"体积约压到十分之一、OCR 准确率几乎无影响"——**这是未验证的断言**。`image_picker` 的质量压缩并非对所有图片格式生效，Web 端行为也可能与移动端不同。
- 验收：用同一张真实课本 / 单词表照片，对比压缩前后**上传体积**与**识别出的单词列表**，把两组数据写进汇报。若识别明显变差，停下来报告，不要自行调参。

### U-2　单词高亮生效并去重

- 现象：目标词 span 与正文样式颜色相同（都是 `Colors.black87`），高亮没有视觉效果；`_buildEnglishSpans` / `_buildChineseSpans` 与 `_SectionCard` 在 `story_page.dart` 与 `history_detail_page.dart` 中逐字重复（约 130 行）。
- 要求：
  1. 让目标词有明显视觉区别：加粗，配合主题主色（用 `Theme.of(context).colorScheme.primary`，不硬编码 `Colors.blue`）；是否加下划线按可读性决定，并在汇报中说明。
  2. 抽出公共组件到 `lib/widgets/highlighted_text.dart`，两个页面共用，删除重复代码。
  3. 保持原有切分逻辑与匹配行为**不变**，只改样式。若发现正则本身有缺陷（如词形变化匹配不到），**只报告，不修**。
  4. 中文侧的高亮沿用现有逻辑（译文里"苹果 (apple)"这种夹注形式）。
- 验收：至少一个 widget 测试——渲染含目标词的文本，断言目标词 span 的样式与普通 span 不同；`flutter analyze` 无新增告警；`StoryPage` 与历史详情页手动查看效果一致。

### U-5　保存反馈与防重复

- 现象：`story_page.dart:16` 保存按钮点击后无提示，可重复点击产生多条记录。
- 要求：
  1. `saveCurrentRecord()` 返回 `bool`，`AppProvider` 维护 `isSaved`（及保存中的状态）。
  2. 保存中按钮不可再点；成功后 `SnackBar` 提示并将按钮置灰或图标切为 `Icons.check`；失败给出提示，且按钮恢复可点。
  3. **产生新故事时 `isSaved` 必须复位**（含 U-1 之后的重新生成路径）。
- 不做：服务端去重（本阶段只做客户端防重复）。
- 验收：手动走一遍——保存成功、保存失败（断网或后端不可达）、保存后重新生成再保存，三种路径行为正确。**联调保存时遵守第 5 节，不写生产库。**

### U-1　识别后插入单词确认页

**动手前先出方案，等我确认（第 4 节第 6 条）。** 方案需包含页面流转图与 `AppProvider` 状态设计。

- 现象：`ocr_page.dart:18` 的 `initState` 触发整条链路，`recognizeText()`（`app_provider.dart:52`）内部直接续接 `_generateStory(words)`，用户没有机会修正 OCR 噪声。
- 目标流程：选图 → 识别 → **单词确认页** → 用户点「生成」→ 短文与填空 → `StoryPage`。
- 要求：
  1. 新增确认页：单词以 `Chip` 展示，可取消勾选 / 删除，可手动添加。
  2. 拆分 `recognizeText()`：识别完成后只保存词表并 `notifyListeners()`，不再自动生成；新增由用户触发的生成入口，接收确认后的词表，内部仍串行 `generateStory → generateFillBlank`（**本阶段不合并接口**，那是 A-1）。
  3. 已选词为空时，「生成」按钮禁用。
  4. 手动添加：去首尾空格、拒绝空串、忽略大小写的重复项。
  5. 从 `StoryPage` 能回到确认页，词表与勾选状态保留，可重新生成，无需重拍。
  6. 识别或生成失败沿用现有 `_error` 机制，并能回到确认页重试。
  7. 保持 U-5 的 `isSaved` 复位。
- 不做：难度选择器（U-8，后续会放在这一页，但本阶段固定沿用 `api_service.dart` 里现有的 `intermediate`）；降级提示（U-4）；任何后端改动。
- 已知局限：OCR 服务不可用时后端会返回固定 mock 词表，确认页无法区分真假。这是 U-4 的问题，本阶段不处理，但汇报里要注明。
- 设计上待确认的两点见第 9 节（待确认项 2、3）。
- 验收：手动路径清单——正常识别并生成、取消部分词后生成、全部取消（按钮禁用）、手动添加（含重复与空串）、生成失败后重试、从 `StoryPage` 返回后重新生成。
